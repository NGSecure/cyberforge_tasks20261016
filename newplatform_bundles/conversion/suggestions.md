1. **待确认单独放一个目录。** 按要求只用了三个目录，待确认和第三类都放在 `newplatform_bundles3/`（表里分开列，`quality.json` 和每个 bundle 的 `cyberforge_source.json` 里 `quality.category` 也分开记）。但待确认的大多数（@@N_ENV@@ 个）只是本机没能构建，原始数据未必有问题；和第三类放在一起，容易被当成“数据有严重问题”而丢掉。建议另设 `newplatform_bundles4/`（或 `newplatform_bundles3/pending/`）。
2. **在合适的机器上验证待确认的 bundle。** 其中 @@N_NET@@ 个要在构建时联网（guetzli、file 没有发布的基础镜像，要从 GitHub 克隆源码并下载 afl 测试样例；serenity、perfetto、arrow 构建时下载依赖），@@N_DISK@@ 个超出本机约 38 GB 的磁盘配额（openssl、fluent-bit、wireshark、unicorn、icu、radare2）。在能直接访问公网、空闲磁盘 100 GB 以上的机器上对它们运行 `build.sh`，按三项自检的结果和数据集证据归入前两类或第三类即可，工具和流程不需要改（`conversion/verify_bundles.py` 可以批量跑并记录）。另外 2 个（assimp WF_LLM_0、cgif WF_RAG_0）是数据集有注入版的崩溃记录、但按它的构建流程编不出注入版，表里给出了预计能解决的最小改动，需要决定是否接受这种改动；kamailio FZ_3 是判定规则的限制（注入在宏里），需要决定是否为它放宽规则。
3. **第三类里有一部分可以补救。** 第三类混合了两种情况：一种是注入本身有问题（注入的代码不在被测程序里、让构建失败、diff 坏了、空输入就触发、只在内存分配失败时才走得到），只能重新设计注入或剔除；另一种是漏洞真实存在、只是数据集没有留下能单独触发的输入（fuzz 过程里写下的崩溃样本单独不复现、报告用的输入没有保存、PoV 在安全版上也触发上游已有的 bug 等，表里“建议”一栏写了“验证后可升为第二类”的那些）。后一种可以用定向 fuzz 或人工构造 PoV 补一个标准答案，但新的标准答案不来自原始数据，建议单独标注来源。建议以后把第三类细分为“需重新设计注入”和“缺可用 PoV”两类。
4. **PASS-DEGENERATE（空输入就能触发）不要用于 PoC 迭代。** 这 @@N_DEGEN@@ 个 bundle 构建和自检都能通过（输出 PASS-DEGENERATE），但提交任何文件都会判为成功，轨迹没有意义；如果只用于不看判定结果的用途（例如代码理解、定位），可以保留。
5. **判定结果的稳定性。** 本机对每个标准答案在两个版本上各运行一次。njs WF_RAG_1 这样触发不稳定的任务，单次运行可能碰巧通过或碰巧失败。建议平台在正式使用前对每个 bundle 的 `/verify` 连续跑 3 次，只保留结果一致的。
6. **构建依赖联网下载、版本没有固定。** guetzli、file 的 setup 克隆的是上游最新代码（再切到 `secure_base_commit`），serenity、perfetto、arrow 构建时下载依赖；上游变化会让以后的构建与数据集当时的不同。建议在能联网的机器上构建一次后把基础镜像固定下来（推送到自己的镜像仓库并按 digest 引用）。
7. **补齐 Git LFS 内容。** 上传的数据集副本缺 @@N_LFS@@ 个 LFS 对象，其中 9 个任务的崩溃种子就在缺的里面（这 9 个任务因此没有生成 bundle）。拿到原始的 LFS 对象后放进 `newplatform_bundles/conversion/lfs_objects/`、重新运行转换即可，用到还原文件的 bundle 也能从第二类回到第一类。
8. **第二类里需要留意的两种情况。** 题面描述按数据集原文保留、只是漏洞类型写得不准的（表里“建议把描述改成实际崩溃类型”），可以统一改描述；注入在 fuzz harness 自己代码里的，漏洞真实、可以正常做 PoC 迭代，但如果训练数据要求漏洞在项目产品代码里，应剔除或单独标注。改正过题面描述的 8 个 bundle（原描述指错了文件或函数），原文保存在 `cyberforge_source.json` 的 `description.original` 里，如不希望改动 agent 看到的题面，可以改回原文，但原描述会明显误导 agent。
