1. **待确认已作为第四类单独放进 `newplatform_bundles4/`**（2026-10-19 的要求）。它们大多只是本机没能构建，原始数据未必有问题，不要和第三类一样直接丢掉；`quality.json` 和每个 bundle 的 `cyberforge_source.json` 里 `quality.category` 仍记作“待确认”。
2. **在磁盘充足的机器上验证第四类里没建成的 bundle。** 网络开通后（2026-10-19），本机已用代理验证了原先因联网而没建成的 guetzli、file、perfetto；剩下 @@N_ENV@@ 个：@@N_DISK@@ 个是本机磁盘不够（本机配额约 38 GB，这些项目安全版、注入版各编一次就超出）：@@DISK_PROJECTS@@；@@N_NET@@ 个（@@NET_TASKS@@）是构建时要从 github.com 下载依赖的源码包，本机的 GitHub 代理不放行（403），备用镜像上又没有这个版本。在空闲磁盘 100 GB 以上、能直连 GitHub 的机器上运行 `build.sh`，按三项自检的结果和数据集证据归入前两类或第三类即可，工具和流程不需要改（`conversion/verify_bundles.py` 可以批量跑并记录）。kamailio FZ_3 是判定规则的限制（注入在宏里），需要决定是否为它放宽规则；它能构建、能推送（自检 3 不通过，build.sh 打印说明后以 BUILT 结束）。
3. **第三类里有一部分可以补救。** 第三类都能构建、能推送（自检 3 不通过的，build.sh 打印说明后以 BUILT 结束），但混合了两种情况：一种是注入本身有问题（注入的代码不在被测程序里、diff 坏了、空输入就触发、只在内存分配失败时才走得到），只能重新设计注入或剔除；另一种是漏洞真实存在、只是数据集没有留下能单独触发的输入（fuzz 过程里写下的崩溃样本单独不复现、报告用的输入没有保存、PoV 在安全版上也触发上游已有的 bug 等，表里“建议”一栏写了“验证后可升为第二类”的那些）。后一种可以用定向 fuzz 或人工构造 PoV 补一个标准答案，但新的标准答案不来自原始数据，建议单独标注来源。建议以后把第三类细分为“需重新设计注入”和“缺可用 PoV”两类。
4. **PASS-DEGENERATE（空输入就能触发）不要用于 PoC 迭代。** 这 @@N_DEGEN@@ 个 bundle（@@DEGEN_SPLIT@@）构建和自检都能通过（输出 PASS-DEGENERATE），但空 PoV 就能通过；@@ANY_SENTENCE@@轨迹没有意义；如果只用于不看判定结果的用途（例如代码理解、定位），可以保留。
5. **判定结果的稳定性。** 本机对每个标准答案在两个版本上各运行一次。njs WF_RAG_1 这样触发不稳定的任务，单次运行可能碰巧通过或碰巧失败。建议平台在正式使用前对每个 bundle 的 `/verify` 连续跑 3 次，只保留结果一致的。
6. **构建依赖联网下载、版本没有固定。** guetzli、file 的 setup 克隆的是上游最新代码（再切到 `secure_base_commit`），serenity、perfetto、arrow 构建时下载依赖；上游变化会让以后的构建与数据集当时的不同。建议在能联网的机器上构建一次后把基础镜像固定下来（推送到自己的镜像仓库并按 digest 引用）。
7. **没有标准答案的 bundle 单独看待。** 数据集缺 @@N_LFS@@ 个 LFS 对象，上游 CyberForge-projects 本身也没有（它把指针当普通文件提交，从未上传过这些对象；上游 README 链接的 Hugging Face 数据集里也只有同样的指针，见 `newplatform_bundles/conversion/upstream_comparison.md`）。缺的大多是不进 bundle 的语料，不影响任何 bundle，所以不再找回；只有 @@N_NOGT@@ 个任务的崩溃种子在缺的里面，按 2026-10-19 的决定照常转成了 bundle，但没有标准答案、不做标准答案自检（@@NOGT_WHERE@@）。验证过的都能构建、能判定，但能否被输入触发没有在本机验证：平台统计成功率时建议把这 @@N_NOGT@@ 个单独列出，不要把它们上的失败直接算作模型能力不足；如果以后从上游作者那里拿到原始种子（按 SHA-256 命名，放进 `newplatform_bundles/conversion/lfs_objects/`）、重新转换，它们就会带上标准答案和完整自检。另外，提供数据的团队补的 16 个 serenity 种子文件（`gsub_tail_*.bin`）内容与指针不符，不影响现有 bundle，但以后用到时应换回原始内容。
8. **第二类里需要留意的两种情况。** 题面描述按数据集原文保留、只是漏洞类型写得不准的（表里“建议把描述改成实际崩溃类型”），可以统一改描述；注入在 fuzz harness 自己代码里的，漏洞真实、可以正常做 PoC 迭代，但如果训练数据要求漏洞在项目产品代码里，应剔除或单独标注。改正过题面描述的 8 个 bundle（原描述指错了文件或函数），原文保存在 `cyberforge_source.json` 的 `description.original` 里，如不希望改动 agent 看到的题面，可以改回原文，但原描述会明显误导 agent。
9. **构建失败或转化不成有效任务的放在 `other_errors/`（第六类，2026-10-19 的要求），不要构建上传。** 原第三、四类的 5 个因原始数据的问题一定构建失败：flex WF_RAG_0、flex WF_RAG_1、openh264 WF_RAG_0（原第三类：注入让构建失败，或两个版本的产物完全相同），assimp WF_LLM_0、cgif WF_RAG_0（原第四类：数据集有注入版的崩溃记录，但按它的构建流程编不出注入版）；后两个在第 6 节的表里给出了预计能解决的最小改动（对构建流程的少量偏离），如果接受，改动后重新转换、验证即可移出。另外 @@N_C56@@ 个原来没有生成 bundle、按第五类的方案也救不了：构建不了的 @@N_C6B@@ 个（注入的代码不在被构建的程序里、diff 让漏洞版编译不过、open62541 的项目构建在数据集镜像里就失败），转化不成有效任务的 @@N_C6U@@ 个（能构建，但注入只是注释或死代码、改动没有可观察的效果、注入是加固、需要 root、网络命名空间或约 10 GB 内存等判定环境给不了的条件）。交给组员构建上传的是其余目录：第一、二类可直接用于 PoC 迭代，第三类和第四类能构建、能推送，但用途受限（见上面几条和第 6 节），第五类见下一条。
10. **第五类按任务实现判定，用法和前几类相同。** @@N_5@@ 个 bundle 的判定规则在各自的 `tests/oracle.json`，能构建的都能推送：可用 @@N_5P@@ 个；没有标准答案的 @@N_5G@@ 个能构建、能判定，但能否被 PoV 触发没有在本机验证（平台统计成功率时建议单独列出）；空 PoV 也通过的 @@N_5D@@ 个不要用于 PoC 迭代（见第 4 条）。已经转化好、只是本机条件不够没能实测的 @@N_5H@@ 个（@@HW_TASKS@@）需要在条件足够的机器上运行 `build.sh` 验证：wireshark、libvips 要 100 GB 以上的磁盘，arrow 要能直连 GitHub（本机代理拒绝 GitHub 的源码包下载），h2o WF_LLM_3 的判定要约 16 GB 内存（部署时任务服务器也要这么大）。第五类的标准答案有的做过最小改写（改写说明在 `cyberforge_source.json` 的 `ground_truth.how_found` 和 `c5_specs.json` 的 `ground_truth.adapted`），新写的 driver 在 `newplatform_bundles/conversion/c5/drivers/`，建议抽查。
11. **判定的已知局限。** 输出差分、输出匹配类的任务（第五类的逻辑漏洞）只要求 PoV 让两个版本的可观察行为不同；两个版本只差注入的 diff，所以差别一定来自注入的改动，但有的题目很简单（第 6 节“影响”里写了“题目很简单”或“较简单”的，如 behaviortreecpp WF_RAG_0、brotli FZ_0、h3 FZ_12、h3 FZ_53）。脚本引擎、程序型 PoV 能自己执行项目代码，可以通过行为差异分辨版本（见 `newplatform_bundles/CONVERSION_REPORT.md` 4.7）。第一至三类里 jq 的 10 个 CLI 型 bundle（leptonica WF_LLM_0 可能也是）运行的是 libtool 包装脚本，判定时它启动的真正程序不可读，进程不可转储，sanitizer 读不到自己的环境变量：判定按“有 sanitizer 报告或致命信号”，本机验证的结果不受影响，但返回给 agent 的崩溃栈没有函数名、exploit 设的 ASAN_OPTIONS 不生效。第五类已改正（判定端让包装脚本启动的程序可读）；按约定第一至四类没有改动，需要时可以用 `convert.py` 统一重新生成。
